Bus de Servicio Empresarial

Es una implementación del patrón de arquitectura de software ESB (Bus de Servicio Empresarial), diseñado para estandarizar e integrar la comunicación entre diferentes aplicaciones en una arquitectura orientada a servicios (REST). Funciona como una capa de abstracción que desacopla los sistemas, permitiendo que interactúen sin tener conocimiento directo de la implementación de los demás.

Su funcionalidad principal es actuar como un intermediario que gestiona el enrutamiento, la transformación y la mediación de mensajes. El CESB establece y aplica reglas de negocio centralizadas a través de APIs, garantizando que la comunicación entre sistemas, tanto internos como de terceros, cumpla con las normativas y políticas de la organización. Esto facilita el acceso controlado a datos específicos y el rastreo de información para resguardar la integridad corporativa.

En términos de seguridad, el CESB implementa un modelo robusto que incluye el cifrado de mensajes y alertas en tránsito, utilizando protocolos seguros como HTTPS. Además, gestiona el enrutamiento de contenidos, la segmentación de datos entre componentes y la creación de enlaces seguros entre aplicaciones y bases de datos, asegurando la confidencialidad e integridad de la información.

Como valor añadido, el CESB integra un servidor web con soporte para HTTP/2.0, lo que optimiza la comunicación mediante técnicas como la multiplexación de flujos y la compresión de cabeceras. También incluye un motor de generación de código que transforma interfaces gráficas HTML en código fuente, acelerando el desarrollo de servicios.

Sandra Server Enterprise (SSE)

Opera como una capa de middleware que implementa el patrón de diseño de mediador. Su función es intermediar en la comunicación entre un cliente y un servicio, actuando como un adaptador de protocolos y formatos de datos. Esta mediación es crucial para asegurar la interoperabilidad entre sistemas heterogéneos que, de otro modo, no podrían comunicarse eficazmente.

En la práctica, las aplicaciones cliente no invocan los servicios finales directamente. En su lugar, dirigen sus peticiones al SSE, que se encarga de transformar la solicitud al formato y protocolo que el servicio de destino espera. De manera similar, procesa la respuesta del servicio para adecuarla al cliente. Este modelo de comunicación indirecta, basado en patrones predefinidos, promueve un bajo acoplamiento y una alta cohesión en la arquitectura.

Como componente integral de la plataforma de middleware de CodeEpic, el SSE es fundamental para la estandarización de servicios y microservicios a nivel organizacional. Al centralizar la lógica de adaptación y mediación, simplifica el desarrollo de los servicios individuales y facilita la gobernanza y gestión del ecosistema de aplicaciones.

API (Interfaz de Programación de Aplicaciones)

Una API (Interfaz de Programación de Aplicaciones) es un contrato formal que define cómo dos o más componentes de software deben interactuar. Consiste en un conjunto de definiciones, subrutinas, protocolos y herramientas que actúan como una capa de abstracción, ocultando la complejidad interna de un sistema y exponiendo únicamente la funcionalidad necesaria de una manera controlada y predecible.

El propósito fundamental de una API es la reutilización de código y la modularidad. Al proporcionar un conjunto de funciones de uso general, las APIs evitan que los desarrolladores tengan que reinventar la rueda, permitiéndoles construir nuevas aplicaciones sobre la funcionalidad existente. Esto acelera el ciclo de desarrollo y reduce la probabilidad de errores.

En el ecosistema de CodeEpic, se establece una dirección estándar para las APIs, que sigue un esquema de versionado semántico (ej. /v1/api/...). Esta URL base actúa como el canal inicial para la gestión de instrucciones y peticiones, asegurando que los clientes siempre interactúen con una versión específica y estable del contrato de la API.

API Bajo Contexto

Atributo Tipo de Dato Descripción y Reglas
IdDriver String Definición clara de un manejador de bases de datos según el contexto.
funcion String Método de acceso como identificador en la línea de ejecución.
ruta String Cadena que permite la ejecución directa de otras APIs o la escalabilidad a otros programas.
parametros String Parámetros enriquecidos según su posición, separados por comas.
metodo String Define el tipo de petición HTTP: GET, POST, PUT, DELETE, OPTIONS.
migrar Bool True para migración, False para no migración.
concurrencia Bool True para concurrencia, False para no concurrencia.
relacional Bool True: Creación por modelo ORM. False: Creación por BigData.
valores Interface{} Declaración de una clase JavaScript. Requiere relacional y coleccion.
coleccion String Nombre de la colección en MongoDB.
consulta String Incluye formatos SQL y NoSQL. Los parámetros en consultas deben empezar con $. Ej: SELECT * FROM tablaA WHERE id = '$0'

Tipos de API en la Plataforma CodeEpic

Tipo Descripción
Código Genera código fuente (JS, TypeScript) a partir de una interfaz gráfica HTML.
Consulta Conecta a una base de datos (SQL o NoSQL) utilizando un driver (Postgres, SQLServer, MySQL, MongoDB).
Interfaz Establece un puente de enlace con otros servicios API para la colaboración entre sistemas.
Archivo Encapsula rutas de descarga de archivos (IMG, PDF, Word) mediante la API, ofreciendo seguridad con JWT.

Métodos de Peticiones HTTP

Método Descripción
GET Solicita una representación de un recurso específico. Solo para recuperar datos.
POST Envía una entidad a un recurso, causando a menudo un cambio en el estado.
PUT Reemplaza todas las representaciones actuales del recurso de destino.
DELETE Borra un recurso específico.
OPTIONS Describe las opciones de comunicación disponibles para el recurso.

Puntos Clave de la Arquitectura

Concepto Descripción
Protocolos HTTP y HTTPS. Este último es la forma cifrada de comunicación entre cliente y servidor. Permite seleccionar puertos.
Función o EndPoint Es el nombre que se le da a una API. Los endpoints son las URLs de un backend que responden a una petición. En un entorno RESTful, un mismo endpoint puede usarse con distintos verbos.
Drivers Elemento de software que facilita la instalación y el uso de tecnologías de asistencia, como bases de datos o servidores.
Consumidores El número máximo de usuarios permitidos para una conexión.
Cache Los datos se alojan en distintos niveles según su frecuencia de uso. El caché inclusivo mantiene una copia en dos o más niveles de memoria.
Entorno Los diferentes ambientes o etapas en el ciclo de vida del desarrollo de software (ej. desarrollo, producción).

Versiones de Revisión (X.Y.Z)

Componente Nomenclatura Significado del Cambio
Versión Mayor X.Y.Z Indica cambios importantes o incompatibilidad con versiones anteriores.
Versión Menor X.Y.Z Denota cambios en el contenido o funcionalidad, pero no una reescritura completa. Se reinicia a 0 cuando la versión mayor cambia.
Segunda Versión Menor X.Y.Z Indica correcciones sin adiciones o eliminaciones relevantes. Suele omitirse si es 0.
Versiones Especiales alpha, beta, release candidate Utilizadas para versiones previas a un lanzamiento oficial, denotando el estado de desarrollo (ej. 2.0-rc1).
