Autorización & JWT

La estrategia de autorización en nuestra arquitectura se centra en el uso de JSON Web Tokens (JWT), un estándar abierto (RFC 7519) que define una forma compacta y autónoma para transmitir información de forma segura entre partes como un objeto JSON. Esta información puede ser verificada y confiada porque está firmada digitalmente.

El enfoque principal es utilizar JWT con una expiración corta, complementado con tokens de refresco (refresh tokens) para mantener la sesión del usuario sin sacrificar la seguridad. La autorización se gestiona mediante un modelo de Control de Acceso Basado en Roles (RBAC), definido en la estructura de datos del usuario.


Historia y Fundamentos de JWT

JWT fue creado por el grupo de trabajo de la IETF (Internet Engineering Task Force) como parte de la especificación de OAuth 2.0 y OpenID Connect. Su objetivo era estandarizar un formato de token que fuera compacto, seguro para URL y utilizable en contextos con restricciones de espacio, como las cabeceras HTTP.


¿Cómo Funciona un JWT?

Un JWT consta de tres partes separadas por puntos (.):

Componente Descripción Detallada Ejemplo (Decodificado)
1. Header (Encabezado) Objeto JSON que identifica qué algoritmo se utilizó para generar la firma.
  • alg: El algoritmo de firma. En nuestro caso, RS256 (firma asimétrica con RSA y SHA-256), que es una práctica de alta seguridad.
  • typ: El tipo de token, que es JWT.
Referencia: RFC 7515, Sec. 4.1 
{
  "alg": "RS256",
  "typ": "JWT"
}
2. Payload (Carga Útil) Contiene las "reclamaciones" (claims), que son declaraciones sobre el usuario y metadatos adicionales. En nuestra arquitectura, aquí se incrusta la estructura completa de Usuario, lo que hace al token autónomo.
  • Reclamaciones Registradas: Estándares como exp (tiempo de expiración) e iss (emisor).
  • Reclamaciones Privadas: Nuestra estructura personalizada Usuario con todos sus roles y permisos.
Referencia: RFC 7519, Sec. 4 
{
  "Usuario": { ...datos... },
  "exp": 1678886400,
  "iss": "Code Epic..."
}
3. Signature (Firma) Se genera para verificar la integridad y autenticidad del token. Se calcula utilizando el encabezado, el payload, una clave secreta (o privada) y el algoritmo especificado en alg. Cualquier modificación en el header o payload invalidará la firma, previniendo la manipulación del token.
Fórmula: RSASHA256(base64Url(header) + "." + base64Url(payload), privateKey)

Implementación en Nuestra Arquitectura

El proceso de autenticación y generación de tokens se inicia en el endpoint /v1/api/wusuario/loginV2. Veamos cómo interactúan el frontend y el backend.

1. Petición desde el Cliente (Angular)

El cliente, en este caso una aplicación Angular, recopila las credenciales del usuario y las envía al backend mediante una petición POST. Es crucial que esta comunicación se realice siempre sobre HTTPS (HTTP/2) para cifrar el canal y proteger las credenciales en tránsito.

// Ejemplo de servicio en Angular para realizar el login
getLogin(user: string, clave: string): Observable {
  let usuario = {
    'nombre' : user,
    'clave' : clave,
  };
  // La URL apunta a nuestro endpoint de login
  let url = this.URL + 'wusuario/loginV2';
  return this.http.post(url, usuario);
}

Nota sobre seguridad: Aunque el canal está cifrado por HTTPS, el backend debe validar y sanear las entradas (`user` y `clave`) para prevenir ataques de inyección SQL. El uso de un ORM o consultas parametrizadas es la práctica recomendada para interactuar con la base de datos de forma segura.

2. Generación del JWT en el Backend (Go)

Una vez que el backend valida las credenciales del usuario, procede a generar el JWT. Nuestra función GenerarJWT utiliza el algoritmo RS256 (RSA con SHA-256), una excelente práctica de seguridad que emplea un par de claves asimétricas (privada y pública).

  • La clave privada se mantiene segura en el servidor y se usa para firmar el token.
  • La clave pública puede ser distribuida a otros servicios para que puedan verificar la autenticidad del token sin necesidad de conocer la clave privada.

// GenerarJWT Json Web Token
func GenerarJWT(u Usuario, tiempo time.Duration) string {
	// Definimos las reclamaciones (claims) del token
	peticion := Reclamaciones{
		Usuario: u, // ¡Aquí incrustamos toda la estructura del usuario!
		StandardClaims: jwt.StandardClaims{
			ExpiresAt: time.Now().Add(tiempo).Unix(), // Claim estándar: Tiempo de expiración
			Issuer:    "Code Epic Technologies",      // Claim estándar: Emisor del token
		},
	}

	// Creamos el token con el algoritmo RS256 y nuestras reclamaciones
	token := jwt.NewWithClaims(jwt.SigningMethodRS256, peticion)

	// Firmamos el token con nuestra llave privada
	rs, e := token.SignedString(LlavePrivada)
	if e != nil {
		system.SystemLog.Println(e.Error() + " Usuario " + u.Nombre)
	}
	return rs
}

3. La Carga Útil (Payload): El Corazón del Token

La gran ventaja de nuestro enfoque es que el payload del JWT contiene toda la información necesaria para la autorización, extraída directamente de nuestra estructura Usuario. Esto hace que el token sea "autónomo": el backend no necesita consultar la base de datos en cada petición para verificar los permisos.

Buenas Prácticas y Normas ISO

Nuestra implementación sigue varias buenas prácticas de seguridad y se alinea con los principios de normativas como la familia ISO/IEC 27000, que se centra en los sistemas de gestión de seguridad de la información.

Ventaja / Buena Práctica Implementada Descripción y Justificación
Tokens Autónomos (Stateless) El servidor no necesita almacenar el estado de la sesión. Toda la información de autorización está en el token, lo que mejora la escalabilidad.
Firma Asimétrica (RS256) Aumenta la seguridad. Permite que los servicios de recursos verifiquen el token con una clave pública, sin poder crearlos, centralizando la emisión de tokens en un servicio de autenticación seguro.
Expiración Corta (ExpiresAt) Limita la ventana de oportunidad para un atacante si un token es robado. Se recomienda usar tokens de corta duración (ej. 15 minutos) junto con refresh tokens para renovarlos.
Comunicación sobre HTTPS Previene ataques de intermediario (Man-in-the-Middle) y asegura que el token no sea interceptado en texto plano. Es un requisito indispensable.
No almacenar datos sensibles en el payload El payload es visible (codificado en Base64, no cifrado). Nuestra estructura Usuario excluye datos críticos como la contraseña (Clave).
Validación del Emisor (Issuer) La claim iss permite al backend verificar que el token fue emitido por una autoridad de confianza ("Code Epic Technologies").
