WebSockets: Comunicación Bidireccional en Tiempo Real

El protocolo WebSocket (RFC 6455) representa un cambio de paradigma fundamental en la comunicación cliente-servidor. A diferencia del modelo transaccional de solicitud-respuesta de HTTP, WebSocket establece un canal de comunicación full-duplex persistente sobre una única conexión TCP. Esto permite un intercambio de mensajes bidireccional y de baja latencia, esencial para aplicaciones en tiempo real como chats, notificaciones instantáneas, dashboards financieros o juegos multijugador.

Historia y Motivación: Superando las Limitaciones de HTTP

Antes de la estandarización de WebSocket en 2011, la implementación de funcionalidades en tiempo real en la web era ineficiente y compleja. El protocolo HTTP, por su naturaleza sin estado, no fue diseñado para mantener conexiones abiertas. Para simular esta capacidad, los desarrolladores recurrieron a diversas técnicas conocidas como Comet:

  • Polling (Sondeo Corto): El cliente realiza peticiones HTTP al servidor a intervalos regulares (ej. cada 2 segundos) para preguntar si hay nuevos datos. Esto genera una sobrecarga masiva de peticiones, la mayoría de las cuales son innecesarias y consumen recursos de red y servidor.
  • Long Polling (Sondeo Largo): El cliente realiza una petición HTTP que el servidor mantiene abierta hasta que tiene nuevos datos para enviar. Una vez enviada la respuesta, la conexión se cierra y el cliente inicia inmediatamente una nueva. Aunque más eficiente que el sondeo corto, sigue sufriendo de la sobrecarga de cabeceras HTTP y la latencia de restablecer la conexión.

WebSocket fue diseñado específicamente para resolver estos problemas, proporcionando un estándar nativo para una comunicación persistente y de baja sobrecarga directamente en el navegador.

Anatomía del Protocolo WebSocket

La "magia" de WebSocket reside en su proceso de establecimiento de conexión y en su estructura de datos.

1. El Handshake de Actualización (The Upgrade Handshake)

Una conexión WebSocket comienza su vida como una petición HTTP/1.1 convencional, lo que le permite atravesar firewalls y proxies existentes. El cliente envía una solicitud GET con cabeceras especiales que solicitan una "actualización" del protocolo: 

GET /sandra_ws HTTP/1.1
Host: servidor.com
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Key: dGhlIHNhbXBsZSBub25jZQ==
Sec-WebSocket-Version: 13

Si el servidor soporta WebSockets, responde con un código de estado 101 Switching Protocols. A partir de este momento, la conexión HTTP se "secuestra" y se convierte en una conexión WebSocket binaria, abandonando por completo el protocolo HTTP.

2. Tramas (Frames) de Datos

Una vez establecida la conexión, la comunicación no se basa en texto HTTP, sino en tramas (frames). Cada mensaje se divide en una o más tramas, que son unidades de datos binarias. Este mecanismo permite enviar mensajes de texto y binarios de forma concurrente sin que se bloqueen entre sí, y es la clave para su baja latencia. Las tramas de control (como Ping/Pong) aseguran que la conexión se mantenga viva incluso en ausencia de datos de la aplicación.

Arquitectura de Mensajería en Sandra Server

Sandra Server implementa un robusto sistema de mensajería WebSocket basado en el patrón de diseño Mediador, comúnmente conocido como "Hub". Este Hub centraliza la gestión de todas las conexiones, mensajes y canales, desacoplando a los clientes entre sí.

Componentes y Endpoints Clave

La arquitectura se expone a través de tres endpoints principales:

Endpoint Método Descripción Técnica
/sandra_ws GET (con cabecera Upgrade) Es el punto de entrada para iniciar la conexión WebSocket. El manejador system.HandleConnections(WSHub, w, r) gestiona el handshake, actualiza la conexión HTTP a WebSocket y registra al nuevo cliente en el WSHub.
/v1/sandra_sessions GET Un endpoint administrativo RESTful que permite consultar el estado del WSHub. El manejador ListClientsHandler(WSHub, w, r) itera sobre los clientes conectados y devuelve una lista de las sesiones activas, útil para monitoreo y depuración.
/v1/sandra_send-message POST Actúa como un puente HTTP a WebSocket. Permite que otros servicios del backend (que no tienen una conexión WebSocket directa) envíen mensajes a clientes específicos o a canales (rooms) a través de una simple petición POST. El manejador SendMessageHandler(WSHub, w, r) recibe la petición, identifica el destinatario y utiliza el WSHub para enrutar el mensaje al cliente o clientes correctos.

Patrones de Diseño Implementados

  • Hub y Spoke (Concentrador y Radio): El WSHub actúa como el concentrador. Cada cliente conectado es un "radio". Los clientes no se comunican directamente, sino a través del Hub, que se encarga de la difusión (broadcast) o el enrutamiento selectivo.
  • Publicar/Suscribir (Pub/Sub): El sistema soporta el concepto de "canales" o "salas" (rooms). Un cliente puede suscribirse a uno o más canales. Cuando un mensaje se publica en un canal (por ejemplo, a través del endpoint /v1/sandra_send-message), el Hub se asegura de que solo los clientes suscritos a ese canal lo reciban. Esto es fundamental para arquitecturas multi-tenant, donde se debe aislar la comunicación entre diferentes organizaciones o grupos de usuarios.
  • Autenticación y Autorización: Aunque no se muestra en el código, es crucial que el manejador de /sandra_ws valide un token (ej. JWT) durante el handshake inicial para autenticar al usuario. Una vez autenticado, el Hub puede asociar la conexión con un ID de usuario y sus roles, aplicando políticas de autorización sobre qué canales puede escuchar o a cuáles puede enviar mensajes.

Para ver una implementación práctica de un cliente WebSocket, puedes consultar el código de demostración en examples/node/websocket.

Conexiones Seguras (WSS) y Autenticación en el Handshake

La seguridad es un pilar no negociable. Las conexiones WebSocket deben establecerse siempre a través de un canal cifrado.

  • ws:// (No seguro): Equivalente a HTTP. El tráfico viaja en texto plano y es vulnerable a la interceptación. Solo debe usarse en entornos de desarrollo locales y controlados.
  • wss:// (Seguro): Equivalente a HTTPS. Utiliza Transport Layer Security (TLS) para cifrar toda la comunicación, desde el handshake inicial hasta cada trama de datos. Es la única opción viable para entornos de producción.

Para habilitar wss://, el servidor debe configurarse para usar TLS, de la misma manera que un servidor web habilita HTTPS. En Go, esto se logra con ListenAndServeTLS. 

// Ejemplo de configuración de un servidor WebSocket seguro en Go
http.HandleFunc("/sandra_ws", func(w http.ResponseWriter, r *http.Request) {
    // ... Lógica de autenticación y actualización de conexión ...
})

log.Println("Servidor WebSocket seguro (WSS) escuchando en :8443")
err := http.ListenAndServeTLS(":8443", "path/to/cert.pem", "path/to/key.pem", nil)
if err != nil {
    log.Fatal("ListenAndServeTLS: ", err)
}

Autenticación mediante Parámetros de URL

El handshake de WebSocket es el momento ideal para autenticar y autorizar a un usuario. Dado que la conexión se inicia con una petición HTTP, podemos usar mecanismos estándar como los parámetros de consulta (query parameters) para pasar credenciales.

Consideremos una URL de conexión como: wss://localhost:8443/sandra_ws?userId=user-123&token=jwt-token-aqui

Dentro del manejador system.HandleConnections, antes de actualizar la conexión, se debe:

  1. Extraer los parámetros: Leer userId y token de la URL de la petición (r.URL.Query()).
  2. Validar el Token: Verificar la firma y la caducidad del JWT. El userId del token debe coincidir con el userId de la URL para evitar suplantaciones.
  3. Asociar la Conexión: Si la validación es exitosa, al registrar el cliente en el WSHub, se debe asociar la conexión con el userId. Esto es fundamental para poder enviar mensajes dirigidos a usuarios específicos más tarde.

Si la autenticación falla, el servidor debe responder con un código de error HTTP (ej. 401 Unauthorized) y no actualizar la conexión a WebSocket.

El Rol de Sandra Server: Pilar de la Comunicación Asíncrona

Sandra Server no es solo un servidor de aplicaciones, sino un pilar de infraestructura diseñado para centralizar y optimizar la comunicación. Su sistema de mensajería WebSocket es clave para aliviar la carga de los servicios de backend y habilitar una comunicación fluida y desacoplada entre distintas partes del ecosistema.

Alivio de Carga en Tareas de Segundo Plano (Background Jobs)

Un caso de uso común es la gestión de tareas de larga duración, como la generación de un informe complejo. El enfoque ineficiente sería que el cliente "preguntara" repetidamente al servidor si la tarea ha terminado (polling).

El enfoque de Sandra Server es mucho más eficiente:

  1. El cliente inicia la tarea con una petición REST estándar: POST /v1/api/generar-informe.
  2. El servidor responde inmediatamente con 202 Accepted y comienza a procesar el informe en una rutina de fondo (goroutine).
  3. El cliente espera pasivamente, manteniendo su conexión WebSocket abierta.
  4. Cuando la tarea finaliza, el servicio de backend no necesita conocer al cliente. Simplemente realiza una única petición interna al endpoint de mensajería de Sandra: POST /v1/sandra_send-message.
  5. El cuerpo de esta petición indica el destinatario y el contenido del mensaje:

El WSHub de Sandra Server recibe esta petición, busca la conexión asociada a user-123 y le "empuja" (push) el mensaje. El cliente recibe la notificación en tiempo real y puede habilitar el botón de descarga. Este patrón elimina cientos de peticiones de sondeo innecesarias, liberando recursos de red y de servidor.

Mensajería Desacoplada entre Aplicaciones

El endpoint /v1/sandra_send-message actúa como un bus de mensajería ligero. Permite que diferentes microservicios se comuniquen con los clientes o entre sí sin tener dependencias directas.

Ejemplo: Flujo de E-commerce

Imaginemos un `Servicio de Pagos` y un `Servicio de Inventario`. Cuando un usuario completa una compra:

  • El Servicio de Pagos, al confirmar la transacción, publica un mensaje en el canal del usuario a través de Sandra Server: {"targetUserId": "user-xyz", "payload": {"event": "pago_confirmado"}}. El frontend del usuario muestra una confirmación inmediata.
  • Simultáneamente, el Servicio de Inventario, que también puede estar suscrito a eventos de pago (mediante otro mecanismo o incluso otro WebSocket), descuenta el stock y, si un producto se agota, puede publicar un mensaje en un canal de administradores: {"targetChannel": "admin_alerts", "payload": {"event": "stock_bajo", "productId": "prod-456"}}.

En este escenario, Sandra Server es el intermediario que permite la comunicación en tiempo real sin que el Servicio de Pagos necesite saber cómo funciona el frontend o qué hace el Servicio de Inventario. Esta arquitectura desacoplada es más resiliente, escalable y fácil de mantener.

Definiendo el Protocolo: El Contrato de Mensajes JSON

Para que el cliente y el servidor se comuniquen de manera efectiva a través de un WebSocket, deben adherirse a un protocolo de aplicación o "contrato". En la arquitectura de Sandra Server, este contrato se define mediante mensajes estructurados en formato JSON. Usar JSON en lugar de texto plano permite enviar datos complejos y dota a cada mensaje de un contexto claro, facilitando su procesamiento en el lado del cliente.

Estructura del Mensaje (Servidor → Cliente)

Cuando el servidor envía un mensaje a un cliente (ya sea por una acción directa o a través del endpoint /v1/sandra_send-message), utiliza una estructura JSON predefinida. Basado en el código del manejador SendMessageHandler, el payload tiene la siguiente forma: 

{
  "id": "admin_message",
  "message": "Este es un mensaje de prueba desde el servidor.",
  "from": "all"
}
Campo Descripción
id Un identificador de tipo de mensaje. Permite al cliente saber cómo interpretar o dónde mostrar el mensaje (ej: "chat_message", "system_notification", "report_ready").
message El contenido principal del mensaje. Puede ser un simple texto o, para datos más complejos, una cadena JSON anidada.
from Indica el origen del mensaje. Puede ser "all" para un broadcast, un ID de usuario específico, o "system" para notificaciones automáticas.

Ejemplos de Implementación en el Cliente

A continuación se muestra cómo diferentes frameworks de frontend pueden recibir y procesar estos mensajes JSON.

Ejemplo en JavaScript Puro

const ws = new WebSocket('wss://localhost:8443/sandra_ws?userId=user-123&token=...');

ws.onmessage = (event) => {
  try {
    // 1. Parsear el string JSON recibido a un objeto JavaScript
    const data = JSON.parse(event.data);

    // 2. Procesar el mensaje según su 'id'
    switch (data.id) {
      case 'admin_message':
        console.log(`Mensaje del admin: ${data.message}`);
        // Lógica para mostrar un banner global
        break;
      case 'chat_message':
        console.log(`Nuevo mensaje de ${data.from}: ${data.message}`);
        // Lógica para añadir el mensaje a una ventana de chat
        break;
      default:
        console.log('Mensaje de tipo desconocido:', data);
    }
  } catch (error) {
    console.error('Error al parsear el mensaje del WebSocket:', error, 'Dato recibido:', event.data);
  }
};

ws.onopen = () => {
  console.log('Conexión WebSocket establecida.');
};

Ejemplo en Angular (con RxJS)

Este ejemplo mejora el servicio WebSocket para que emita objetos JSON parseados, simplificando su consumo en los componentes.

// En tu WebSocketService
import { Subject } from 'rxjs';
import { map } from 'rxjs/operators';

// ...
private messagesSubject = new Subject();
public messages$ = this.messagesSubject.asObservable().pipe(
  map(messageStr => JSON.parse(messageStr)) // Transforma el string a JSON
);

// ... en el constructor o método connect()
this.ws.onmessage = (event) => {
  this.messagesSubject.next(event.data as string);
};

// En tu componente
this.webSocketService.messages$.subscribe(data => {
  // 'data' ya es un objeto JSON
  if (data.id === 'reporte_generado') {
    this.downloadUrl = data.message.url_descarga; // Accediendo a un JSON anidado
    this.showNotification = true;
  }
});

Ejemplo en Vue.js 3 (Composition API)

<script setup>
import { ref, onMounted, onUnmounted } from 'vue';

const messages = ref([]);
const connectionStatus = ref('Conectando...');
let ws = null;

onMounted(() => {
  ws = new WebSocket('wss://localhost:8443/sandra_ws?userId=user-vue&token=...');

  ws.onopen = () => {
    connectionStatus.value = 'Conectado';
  };

  ws.onmessage = (event) => {
    try {
      const data = JSON.parse(event.data);
      messages.value.push(data); // Añade el objeto al array reactivo
    } catch (e) {
      console.error('Mensaje no es JSON válido:', event.data);
    }
  };

  ws.onclose = () => {
    connectionStatus.value = 'Desconectado';
  };
});

onUnmounted(() => {
  if (ws) {
    ws.close();
  }
});
</script>

Ejemplo de Envío desde un Servicio Externo (Python)

Así es como un microservicio escrito en Python podría usar el endpoint /v1/sandra_send-message para notificar a un cliente que su tarea ha finalizado.

import requests
import json

# URL del puente HTTP a WebSocket de Sandra Server
SANDRA_MESSAGE_URL = "http://localhost:8080/v1/sandra_send-message"

def notificar_cliente(user_id, status, download_url):
    """
    Envía una notificación a un cliente específico a través de Sandra Server.
    """
    # El payload del mensaje que recibirá el cliente
    client_payload = {
        "event": "reporte_generado",
        "status": status,
        "url_descarga": download_url
    }

    # La estructura de la petición para el endpoint de Sandra
    request_body = {
        "clientId": user_id,
        "message": json.dumps(client_payload) # El payload se envía como un string JSON
    }

    try:
        response = requests.post(
            SANDRA_MESSAGE_URL,
            json=request_body,
            headers={"Content-Type": "application/json"}
        )
        if response.status_code == 200:
            print(f"Notificación enviada exitosamente al usuario {user_id}")
        else:
            print(f"Error al notificar: {response.status_code} - {response.text}")
    except requests.exceptions.RequestException as e:
        print(f"Error de conexión al notificar: {e}")
