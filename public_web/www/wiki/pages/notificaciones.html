Notificaciones & Alertas

La plataforma Sandra Server ofrece un robusto sistema de notificaciones que va más allá de las alertas en la aplicación. Implementa el estándar Web Push, que permite a una aplicación web enviar notificaciones a un usuario incluso cuando este no tiene el sitio web abierto. Esto se logra a través de Service Workers, scripts que el navegador ejecuta en segundo plano, y un sistema de alertas tempranas basado en reglas de negocio.

Arquitectura de Notificaciones Web Push

El protocolo Web Push involucra tres actores principales: la aplicación cliente (navegador), un Push Service (un intermediario proporcionado por el fabricante del navegador, como Google o Mozilla) y nuestro servidor de aplicaciones (Sandra Server). Para que nuestro servidor pueda identificarse de forma segura ante el Push Service, utiliza el estándar VAPID.

¿Qué es VAPID y para qué sirve?

VAPID (Voluntary Application Server Identification) es una especificación (RFC 8292) que permite a un servidor de aplicaciones identificarse de forma segura ante un Push Service. Funciona mediante un par de claves criptográficas (pública y privada):

  • Clave Privada: Se mantiene secreta en Sandra Server. Se utiliza para firmar cada notificación push que se envía.
  • Clave Pública: Se comparte con el cliente (navegador). Cuando el cliente se suscribe a las notificaciones, le presenta esta clave pública al Push Service, indicándole que solo debe aceptar notificaciones firmadas por la clave privada correspondiente.

El uso de VAPID es fundamental porque elimina la necesidad de registrarse en plataformas específicas de cada proveedor (como el antiguo Firebase Cloud Messaging), proporcionando un método estándar y universal para autenticar las notificaciones.

Flujo de Comunicación y Endpoints Clave

El proceso de suscripción y envío de notificaciones se orquesta a través de tres endpoints principales en Sandra Server.

Endpoint Método Descripción Técnica
/v1/api/wpush/vpk GET Obtener Clave Pública VAPID: El frontend llama a este endpoint para obtener la clave pública VAPID del servidor. Esta clave es necesaria para que el navegador pueda solicitar una suscripción al Push Service en nombre de nuestra aplicación.
/v1/api/wpush/subscribe POST Registrar Suscripción: Una vez que el usuario acepta los permisos, el navegador genera un objeto PushSubscription (que contiene la URL del Push Service y las claves para el cifrado). El frontend envía este objeto JSON al backend, que lo almacena en MongoDB, asociándolo con el ID del usuario.
/v1/api/wpush/send POST Enviar Notificación: Este endpoint es utilizado por otros servicios del backend o un panel de administración para iniciar el envío de una notificación. Recibe un cuerpo JSON que especifica el destinatario (userId, groupId o campaignId) y el contenido del mensaje. El manejador busca las suscripciones en MongoDB, construye el payload y lo envía al Push Service correspondiente, firmando la petición con la clave privada VAPID.

Generación de Claves VAPID

Las claves VAPID (pública y privada) son la identidad de tu servidor de aplicaciones y deben generarse una sola vez. La clave privada debe almacenarse de forma segura en las variables de entorno de tu servidor y nunca debe exponerse, mientras que la clave pública se enviará a los clientes a través del endpoint /v1/api/wpush/vpk.

A continuación, se muestran ejemplos de cómo generar este par de claves. Este es un proceso que se realiza una única vez durante la configuración del proyecto.

Node.js (usando la librería web-push)

La forma más sencilla es usar el CLI que proporciona la librería web-push.

# 1. Instalar web-push globalmente o usar npx
npm install -g web-push

# 2. Ejecutar el comando para generar las claves
web-push generate-vapid-keys

# =======================================
# Salida:
# Public Key:
# BEl62i_2...
# Private Key:
# _R-3_tT...
# =======================================

Python (usando la librería py_vapid)

Esta librería proporciona una herramienta de línea de comandos para la generación de claves.

# 1. Instalar la librería
pip install py-vapid

# 2. Generar las claves
vapid --gen

# =======================================
# Salida:
# private_key = "..."
# public_key = "..."
# =======================================

Guarda estas claves en un lugar seguro, como las variables de entorno de tu aplicación, para que el servidor pueda usarlas al firmar las notificaciones.

Identificación Única del Cliente (UUID)

Para que el servidor pueda enviar notificaciones dirigidas a un usuario o dispositivo específico, es crucial asociar cada PushSubscription con un identificador único. Este es el propósito del campo userId en el modelo de datos de MongoDB. Si bien un usuario autenticado ya tiene un ID, para usuarios anónimos o para identificar un navegador específico, podemos generar y persistir un Identificador Único Universal (UUID) directamente en el cliente.

El siguiente ejemplo práctico muestra una función compatible con navegadores para generar un UUID v4. Esta función verifica si ya existe un ID en el localStorage del navegador; si no, genera uno nuevo y lo guarda. Esto asegura que el mismo navegador mantenga el mismo ID entre sesiones.

Ejemplo Práctico en TypeScript/JavaScript

Este código puede ser parte de un servicio en Angular, Vue o cualquier aplicación JavaScript.

/**
 * Genera o recupera un UUID v4 para identificar de forma única al cliente/navegador.
 * Persiste el ID en localStorage para mantenerlo entre sesiones.
 * @returns {string} El UUID v4 del cliente.
 */
function getClientId(): string {
  let id = localStorage.getItem('userId');
  if (!id) {
    // Generador de UUID v4 compatible con todos los navegadores.
    id = 'xxxxxxxx-xxxx-4xxx-yxxx-xxxxxxxxxxxx'.replace(/[xy]/g, function (c) {
      const r = Math.random() * 16 | 0, v = c === 'x' ? r : (r & 0x3 | 0x8);
      return v.toString(16);
    });
    localStorage.setItem('userId', id);
  }
  return id;
}

Este ID generado es el que se debe enviar al backend junto con el objeto de suscripción al llamar al endpoint /v1/api/wpush/subscribe, permitiendo así la segmentación y el envío de notificaciones dirigidas.

Gestión de Campañas y Mensajes con MongoDB

La flexibilidad de MongoDB como base de datos NoSQL es ideal para gestionar las suscripciones y las campañas de notificaciones.

Modelo de Datos en MongoDB

Se pueden utilizar dos colecciones principales:

  1. push_subscriptions: Almacena la información de cada suscripción.
    2. {
  "_id": ObjectId("..."),
  "userId": "user-123",
  "subscription": {
    "endpoint": "https://fcm.googleapis.com/fcm/send/...",
    "expirationTime": null,
    "keys": {
      "p256dh": "...",
      "auth": "..."
    }
  },
  "createdAt": ISODate("...")
}
  2. push_campaigns: Define las campañas, permitiendo mensajes dinámicos y segmentación.
    3. {
  "_id": ObjectId("..."),
  "campaignName": "Oferta de Verano 2024",
  "targetGroup": "clientes_vip", // Segmento de usuarios
  "messageTemplate": {
    "title": "¡Hola, {{user.name}}! Tenemos una oferta para ti",
    "body": "Disfruta de un 20% de descuento en tu próxima compra.",
    "icon": "/assets/icons/icon-96x96.png",
    "data": { "url": "/ofertas/verano" }
  },
  "scheduledAt": ISODate("..."),
  "status": "pending" // pending, sending, completed
}

Cuando se ejecuta una campaña, el backend puede buscar todos los usuarios del grupo clientes_vip, obtener sus suscripciones de push_subscriptions, personalizar el mensaje con sus datos (ej. reemplazar {{user.name}}) y enviar las notificaciones.

Diseño de Campañas de Notificaciones

Para que las notificaciones sean efectivas y no intrusivas, es crucial un buen diseño de campaña.

Principio Descripción ¿Cuándo Usarlo?
Segmentación No enviar el mismo mensaje a todos. Agrupar usuarios por comportamiento, intereses o demografía. Siempre. Es la base de la relevancia.
Personalización Usar datos del usuario (nombre, historial de compras) para hacer el mensaje más personal y relevante. En mensajes transaccionales y de marketing para aumentar la conexión.
Relevancia y Oportunidad Enviar el mensaje en el momento adecuado. Una notificación de "carrito abandonado" es útil una hora después, no un día después. Para notificaciones basadas en acciones del usuario (transaccionales).
Llamada a la Acción (CTA) Clara Indicar claramente qué se espera que haga el usuario. "Ver oferta", "Completar compra". En todas las notificaciones que busquen una interacción.
Control de Frecuencia Limitar el número de notificaciones que un usuario recibe en un período de tiempo para evitar la fatiga y la anulación de la suscripción. Siempre. Es vital para la retención de usuarios.
