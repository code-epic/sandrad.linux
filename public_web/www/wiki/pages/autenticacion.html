Autenticación y Seguridad Híbrida

Es un sistema de autenticación robusto desarrollado en Go, que integra validación de identidad (LDAP/Local), protección contra ataques de fuerza bruta mediante Memoria Local Fragmentada (Sharding) y persistencia de bloqueos en MongoDB con mecanismos de auto-eliminación TTL.

Flujo de Arquitectura de Seguridad

El siguiente modelo describe el ciclo de vida de una petición de autenticación, desde la validación perimetral hasta la emisión del token:

sequenceDiagram
    participant U as Cliente (Frontend)
    participant W as WAF (Detect Injection)
    participant ML as Memoria Local (LoginTracker)
    participant DB as MongoDB (TTL Block)
    participant L as LDAP / DB Local
    participant J as JWT Generator

    U->>W: POST /login (Credenciales)
    W->>W: Validar Inyección SQL/NoSQL
    alt Intento Malicioso
        W-->>U: 403 Forbidden (Error de Credenciales)
    else Limpio
        W->>DB: Consultar si está Bloqueado
        alt Usuario Bloqueado
            DB-->>U: 403 (Cuenta bloqueada temporalmente)
        else Permitido
            W->>L: Validar Credenciales
            alt Credenciales Inválidas
                L->>ML: Incrementar Contador Fallido (Incr)
                ML-->>U: 403 (Error de Credenciales)
                opt Umbral Alcanzado (3 intentos)
                    ML->>DB: Bloquear en MongoDB (TTL 15 min)
                end
            else Credenciales Válidas
                L->>ML: Resetear Contador (Memoria)
                L->>DB: Eliminar Bloqueo (Si existía)
                L->>J: Generar Token JWT
                J-->>U: 200 OK (Token + Contenido)
            end
        end
    end

Componentes de Seguridad y Reglas Técnicas

1. Protección WAF (Web Application Firewall)


Antes de procesar cualquier dato, el sistema utiliza el paquete waf para detectar patrones de inyección en el nombre de usuario.

Regla: Si validate.Injection detecta caracteres o comandos maliciosos, la solicitud se aborta inmediatamente sin consultar la base de datos, protegiendo la integridad del motor de búsqueda.

2. Memoria Local Fragmentada (LoginTracker)


Para gestionar los intentos fallidos con alta eficiencia y concurrencia, el sistema implementa una estructura de Sharding (Fragmentación) alojada en el Heap de la memoria RAM del servidor Go. Esta técnica es crítica para evitar cuellos de botella (Lock Contention) cuando miles de usuarios intentan autenticarse simultáneamente.

Arquitectura de 32 Fragmentos (Shards)

En lugar de utilizar un único mapa protegido por un Mutex global (lo que obligaría a todos los usuarios a hacer fila uno por uno para validar sus intentos), dividimos el espacio de memoria en 32 fragmentos independientes.

Concepto Técnico Definición y Comportamiento en Memoria
Shard (Fragmento) Una subdivisión lógica de la memoria. Cada uno de los 32 shards gestiona aproximadamente el 3.12% del total de usuarios. Cada shard posee su propio cerrojo (sync.RWMutex).
Función Hash Algoritmo determinista (ej. FNV-1a) que decide dónde vive un usuario: shard_id = hash(usuario) % 32. Esto distribuye la carga uniformemente.
Consumo de RAM Extremadamente eficiente. Almacena solo string (login) + int (intentos) + time. 100,000 usuarios activos consumen apenas ~20MB de RAM.
Concurrencia Permite que hasta 32 hilos de ejecución (Goroutines) escriban en memoria simultáneamente sin bloquearse entre sí, aumentando el throughput en un factor de ~30x frente a un mapa estándar.

Ejemplo de Distribución Lógica

// Representación conceptual: 2 usuarios no se bloquean entre sí
Usuario "Ana"  -> Hash("Ana") % 32 = 5   -> Accede al Shard[5] (Lock A)
Usuario "Luis" -> Hash("Luis") % 32 = 12 -> Accede al Shard[12] (Lock B)

// Resultado: Ambos procesos ocurren en paralelo real.
// Solo habría espera si dos usuarios caen en el mismo Shard (probabilidad 1/32).

3. Persistencia de Bloqueo y TTL en MongoDB


Cuando un usuario supera el límite de INTENTOSFALLIDOS_MAXIMOS (definido en 3), el sistema escala el bloqueo de la memoria volátil a la persistencia en MongoDB.

Icono Mecanismo Técnico Descripción y Regla de Negocio Estándar ISO / Seguridad
Índice TTL (Time-To-Live) MongoDB elimina automáticamente el documento cuando la fecha del campo expira es alcanzada. Regla: expireAfterSeconds: 0 significa que expira exactamente en la fecha almacenada. ISO/IEC 27001:2013 A.9.4.2
Restricción de tiempos de conexión y bloqueo automático tras fallos.
Upsert Atómico Se utiliza UpdateOne con upsert: true. Si el bloqueo ya existe, se actualiza el tiempo; si no, se crea. Garantiza que no haya duplicados ni condiciones de carrera. Integridad de Datos
Prevención de inconsistencias en el estado de seguridad del usuario.

Implementación de Índices en MongoDB

Para que el mecanismo funcione, es crítico crear los índices correctamente en la colección de intenciones fallidas:

// 1. Índice TTL: El documento se borra cuando la fecha en 'expira' pasa.
db.intencion.createIndex({ "expira": 1 }, { expireAfterSeconds: 0 })

// 2. Índice Único: Garantiza un solo registro de bloqueo por usuario.
db.intencion.createIndex({ "usuario": 1 }, { unique: true })

// 3. 2. Índice Único: Garantiza una sola sesión de usuario activa por usuario.
db.getCollection("usuario-sesion").createIndex({ "usuario": 1 }, { unique: true });

// 4. Índice TTL: El documento se borra cuando la fecha en 'expira' pasa.
db.getCollection("usuario-sesion").createIndex({ "expira": 1 }, { expireAfterSeconds: 0 });

Lógica de Bloqueo en Go

La función BloquearEnMongo calcula el tiempo de expiración basándose en la configuración del sistema (TIEMPO_BLOQUEO) y realiza la operación de upsert. 

func BloquearEnMongo(login string) {
	c := system.MongoDB.Collection(system.CINTENCIONESFALLIDAS)
	// Bloqueo por 15 minutos
	expira := time.Now().Add(time.Duration(system.TIEMPO_BLOQUEO) * time.Minute)

	filter := bson.M{"usuario": login}
	update := bson.M{
		"$set": bson.M{
			"usuario": login,
			"expira":  expira,
			"fecha":   time.Now(),
		},
	}
	opts := options.Update().SetUpsert(true)
	_, _ = c.UpdateOne(system.Contexto, filter, update, opts)
}

4. Autenticación con TOTP


La implementación de TOTP (Time-based One-Time Password) responde a una estrategia de defensa en profundidad, elevando el nivel de aseguramiento de identidad (LoA) mediante un segundo factor (2FA) que no depende de la conectividad de red ni de servicios de terceros vulnerables (como SMS). Este mecanismo se basa en el estándar abierto RFC 6238, garantizando interoperabilidad nativa con ecosistemas como Google Android y Apple iOS.


Justificación Normativa y Legal


  • NIST SP 800-63B (Digital Identity Guidelines): Clasifica a TOTP como un autenticador criptográfico multi-factor (AAL2/AAL3), técnicamente superior a SMS/PSTN. [Referencia NIST]
  • ISO/IEC 27001:2013 (Control A.9.4.3): Gestión de sistemas de contraseñas y autenticación segura.
  • GDPR (RGPD) Art. 32: Exige medidas técnicas apropiadas (como 2FA) para garantizar la seguridad del procesamiento de datos personales.
  • PSD2 (Directiva Europea): Cumple con los requisitos de "Autenticación Reforzada de Clientes" (SCA) bajo el criterio de Posesión (el dispositivo móvil).

Ventajas de TOTP Offline (Sin Internet)

Ventaja Estratégica Descripción Técnica
Resistencia a SIM Swapping El secreto (semilla) se almacena localmente en el dispositivo. No viaja por la red telefónica, eliminando el riesgo de interceptación de SMS.
Disponibilidad Total (Air-Gapped) El algoritmo se ejecuta localmente. Funciona en modo avión, zonas sin cobertura o redes restringidas.
Privacidad (Zero-Knowledge) El servidor no envía el código al usuario; ambos extremos lo calculan independientemente basándose en el tiempo.

Ejemplo Dinámico del Algoritmo (RFC 6238)

El código se regenera cada 30 segundos. La validación matemática sigue este flujo lógico:

// 1. Secreto Compartido (Base32) y Tiempo Actual
Secret = "JBSWY3DPEHPK3PXP" 
Time   = Floor(UnixTime / 30) // Ventanas de 30 seg desde 1970

// 2. Criptografía HMAC-SHA1
Hash   = HMAC-SHA1(Secret, Time)

// 3. Truncamiento Dinámico
Offset = Hash[last_byte] & 0x0F
Binary = (Hash[Offset]...Hash[Offset+3]) & 0x7FFFFFFF

// 4. Generación del PIN
TOTP   = Binary % 1000000 // Resultado: 6 dígitos (ej. 582 394)

Aplicaciones y Plugins Compatibles

Al ser un protocolo estandarizado, permite al usuario elegir su herramienta de confianza:

  • Google Authenticator: Estándar de facto en Android.
  • Apple iOS (Llavero): Integrado nativamente en Configuración > Contraseñas (desde iOS 15).
  • Microsoft Authenticator: Común en entornos corporativos Azure/365.
  • FreeOTP: Alternativa Open Source mantenida por Red Hat.
  • Plugins de Navegador: Bitwarden, 1Password, Authenticator (Extensión Chrome/Edge).

Reglas de Negocio y Cumplimiento Normativo (ISO/IEC 27001)

Icono Regla de Seguridad Explicación Técnica y Mecanismo Normativa ISO / Estándar
Bloqueo Preventivo Persistente Se implementa un mecanismo de Throttling. Si intentos >= 3, se invoca seguridad.BloquearEnMongo. La persistencia garantiza que el bloqueo sobreviva a reinicios del servidor (stateless), mitigando ataques de fuerza bruta continuos. ISO/IEC 27002 Control 9.4.2
Procedimientos seguros de inicio de sesión. Limitar el número de intentos fallidos permitidos.
Restablecimiento de Estado (Auto-Healing) Tras una autenticación exitosa (200 OK), se ejecuta tracker.Reset y seguridad.DesbloquearEnMongo. Esto asegura la disponibilidad para usuarios legítimos, limpiando contadores en memoria y flags en BD. Principio de Disponibilidad (CIA)
Garantizar el acceso a usuarios autorizados y prevenir la denegación de servicio por bloqueo accidental.
Opacidad en Errores (Anti-Enumeración) El sistema responde con http.StatusForbidden (403) genérico. No se diferencia entre "usuario no encontrado" y "contraseña incorrecta" para evitar la Enumeración de Usuarios. OWASP ASVS 2.1.2
Verificar que las respuestas de error no revelen información sobre la existencia de cuentas.

Generación de Traza (Auditoría)

El sistema cumple con el principio de No Repudio y Monitoreo Continuo. Cada intento de acceso, sea exitoso o fallido, genera un objeto TrazaUser que se almacena en la colección traza. 

traza.Fecha = time.Now()
traza.IP = ip[0] // Capturada del RemoteAddr
// Almacenamiento asíncrono en MongoDB
c := system.MongoDB.Collection("traza")
_, err := c.InsertOne(system.Contexto, traza)
